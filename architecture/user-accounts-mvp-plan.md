# User accounts — MVP plan (FR-ACC-1..3)

**Status:** Decided — **approach B** was chosen and recorded as
[ADR-0017](../adr/0017-passwordless-email-sign-in.md), which closes **T9 — Auth**
([technology architecture §T9](05-technology-architecture.md#t9--auth)). This page remains
the supporting comparison behind that decision, the way
[tech-stack-options.md](tech-stack-options.md) supports ADR-0010.

## 1. What we are building

| Requirement | Issue | MVP meaning |
| --- | --- | --- |
| [FR-ACC-1](../requirements/functional-requirements.md#account--profile-fr-acc--capability-c9) | [#14](https://github.com/rekfar/docs/issues/14) | A visitor can create an account and prove they control the email address. |
| FR-ACC-2 | [#15](https://github.com/rekfar/docs/issues/15) | A user can start and end an authenticated session; user-data endpoints reject anonymous callers. |
| FR-ACC-3 | [#16](https://github.com/rekfar/docs/issues/16) | A user can read and change display name and locale (`nb-NO`). |

This is the whole of [UC-1](../use-cases/use-cases.md#uc-1--register-and-set-up-an-account)
except FR-ACC-4 (default privacy), which is one column and a default value and is cheap to
carry along. FR-ACC-5 (deletion) and FR-ACC-6 (password reset) stay out of this slice —
though note that **the choice made here can remove FR-ACC-6 entirely**.

## 2. What constrains the choice

- **[P1](principles.md#p1-hobby-first-cost-minimal)** — running cost stays at zero; no paid tier.
- **[P7](principles.md#p7-simple-before-clever)** — one maintainer; the least machinery that works.
- **[P9](principles.md#p9-privacy-by-default)** / NFR-PRIV-2 — collect the minimum; an account is
  an email address, a display name, and a locale.
- **[ADR-0010](../adr/0010-tech-stack-dotnet-azure-sql.md)** already names *ASP.NET Core Identity,
  email + password, cookie/JWT, OAuth addable later* as the working assumption for T9. That
  assumption is what this plan tests before we build on it.
- **[ADR-0013](../adr/0013-schema-owned-by-sql-database-project.md)** — whatever we choose, the
  user table lives in the `auth` schema of the SQL Database Project, not in a migration
  generated by the backend.
- **NFR-SEC-2/3** — passwords hashed if we have them; every user-data endpoint authenticated.

## 3. The approaches

| | Approach | How login works | Passwords stored? | Cost | Weight |
| --- | --- | --- | --- | --- | --- |
| **A** | ASP.NET Core Identity, email + password | Password form → cookie/JWT | **Yes** (hashed) | 0 | Medium — plus reset, lockout, breach-list hygiene |
| **B** | Identity, **passwordless email link / one-time code** | Enter email → click link or type 6-digit code → cookie | **No** | 0 + email sending | Low |
| **C** | **Social OAuth / OIDC only** (Google, and/or GitHub) | Redirect to provider → callback → cookie | **No** | 0 | Lowest to build |
| **D** | **Managed identity provider** (Entra External ID, Auth0, Clerk, …) | Hosted login page → OIDC tokens | **No** (not by us) | Free tier, verify limits | Low to build, new dependency to own |
| **E** | **Passkeys / WebAuthn** | Device biometric or security key | **No** | 0 | Highest — needs a recovery path anyway |

A, B and C are not exclusive: Identity supports all three against one user store, so the
account row is the same and the login method is a column. That is the main reason to prefer
staying inside Identity for the MVP rather than adopting D.

## 4. Can we do this without storing any passwords?

**Yes — three of the five approaches never see a password**, and two of them (B and C) cost
nothing and fit the stack ADR-0010 already chose.

The argument for **B (email magic link / one-time code)** in particular:

- **The email infrastructure is not extra work.** FR-ACC-1 requires confirming the address
  anyway, so we need transactional email regardless. Passwordless reuses exactly that.
- **It deletes work rather than adding it.** No password hashing policy, no strength rules,
  no reset flow (FR-ACC-6 becomes moot), no lockout tuning, no credential-stuffing surface,
  and nothing worth stealing if the database leaks.
- **It is not a fork in the road.** ASP.NET Core Identity issues and validates these tokens
  natively; a user row simply has no password hash. Adding a password, a social provider, or
  passkeys later is additive against the same `auth` schema.
- **The honest cost:** login depends on email deliverability and latency (a slow inbox is a
  slow login), and the email account becomes the single point of compromise — which it
  already is in any system with a password-reset flow.

**C (social OAuth only)** is the cheapest of all to build and delegates the security wholly,
but it requires every user to hold a Google/GitHub account, sends a Norwegian hiking log's
user base through a third party (P9, NFR-PRIV-5), and leaves us with no account for someone
who has neither.

## 5. The decision

**B — accepted as [ADR-0017](../adr/0017-passwordless-email-sign-in.md).** ASP.NET Core
Identity as the user store and session issuer, a one-time code emailed to the user as the
only credential, no password column populated, and an `HttpOnly` cookie session. This keeps
ADR-0010's T9 choice (Identity, cookie) intact while dropping the part of it that carries the
most risk and the most code for a one-person project. C and E stay additive on the same user
row if we ever want them.

## 6. Delivery outline

Three thin slices, in order, each shippable:

1. **`database`** — `auth` schema: user table (id, email, email-confirmed, display name,
   locale, default privacy, timestamps) plus Identity's token/login tables, in the DACPAC.
2. **`backend`** — `/v1/auth` (request code, verify, sign out) and `/v1/me` (read, update
   profile); authentication required on every user-data endpoint; rate limiting on the
   request-code endpoint (NFR-SEC-4).
3. **`webapp`** — Norwegian sign-in screen, the "check your email" state, and a profile page.

Each PR closes its slice against `rekfar/docs#14`, `#15`, `#16` per the
[traceability convention](../requirements/README.md).

## 7. What ADR-0017 settled, and what is still open

Settled there: code-in-email over link-in-email, an `HttpOnly` cookie session rather than a
bearer token, code lifetime and attempt caps, and that registration and login are one flow.
NFR-SEC-2 and FR-ACC-1 have been reworded to match.

Still open:

- **Which transactional email provider**, on a free tier, in an EEA region, with
  custom-domain SPF/DKIM. The one sub-decision ADR-0017 leaves for later.
- **Session length**, and what "log out everywhere" should mean in the UI.
- **FR-ACC-6** (reset a forgotten password) is moot as written but not yet retired — a
  passwordless account still needs an answer to "I lost access to my email".
